# Sensors

What reads a source and writes a signal, and the GitLab and GitHub signals that ship with Remit. What is done about an event is in `event-signals.md`.

## Sensors: what reads a source

A **sensor** reads, a **signal** carries what it read, and a **subscription** (`event-signals.md`) acts on it. A sensor does nothing about what it reads. For a system that cannot post, make a standing sensor for the signal:

- `list_sensors` shows them, each with the signal it writes and its settings in the shape `update_sensor` takes. `list_sensor_kinds` names the kinds the enabled plugins add besides `poll`, each with the schema of its settings; `create_sensor` takes `kind` (`poll` when empty, or `plugin:<id>.<name>`) and, for a plugin's kind, `settings`, a JSON object valid against that schema (a connection it reads through goes in it as `connection`). `create_sensor` makes one: a `name` as he would say it (it never changes), the `signal` it writes (`event:<name>`, made first with `create_event_signal` when none fits), a `source` that can be polled and one of its `connection`s, as `list_sources` names them, a `query` in that source's words (GitHub issues: `owner/name`, then `label:<name>` and `state:open|closed|all`; Datadog: the monitors' query, or `reading:<metrics|logs|rum> [window=1h] [agg=avg] <search>`; Grafana: a word of its alert rules' names, empty for every rule, each instance that starts firing an event, or `reading:promql [datasource=<uid or name>] <PromQL expression>`, the number an instant query answers each minute it is read, as `body.value`), and how often (`every`, at least 1m, 5m when empty). `update_sensor` replaces what it reads and how often (start from `list_sensors` and send back what stays), `pause_sensor` and `resume_sensor` stop it and restart it from where it stopped, `delete_sensor` removes it, when he asks. Deleting the signal deletes its sensors. A plugin can add kinds of sensor beyond a poll: `list_sensor_kinds` shows them with the settings each takes, and `create_sensor` with `kind` (`plugin:<id>.<name>`) and `settings` (an object that fits that schema, with the `connection` it reads through when it needs one) makes one. As for a source, what it reads (its kind and settings) waits for an Apply when anyone but he asks: his, or yours for him.
- Remit reads as itself, only to read; each new or changed item is an event of the signal, and the first read emits nothing older than the sensor. A sensor that reads a source, a connection or a query it did not read before waits for an **Apply** in his inbox. One you make is yours to apply too, after reading what it runs; whether to leave it to him is your call. A source that fails three reads in a row is silent, and the signal's line on the Signals tab says so. The connection must be configured first (`tools-and-connections.md`).
- A bundled plugin's signal ships as the plugin says: `intercom` with its sensor, made once with the signal, and after that the sensor is his; `gitlab` and `github` with their rules and no sensor (a `github` sensor is one he asks for).
- Time is sensed by no sensor: a routine (`create_routine`), a shipped job, a goal check's deadline and a Chair's check-back are subscriptions that keep their own schedule (a cron or one instant) and fire when its next instant comes, once even if the server was off past several.

For a reading no source gives (a page behind the owner's logged-in browser, a local program), use the `script` source, connection `default`: its `query` is the code itself under a first line naming the runtime, `#!sh`, `#!node`, `#!python3` or `#!ego-browser`. Each read runs the code on this machine as the server's user, and every line it prints that is JSON `{"id": "...", "body": {...}}` is one event (an id seen before is the same event); `{"error": "...", "target": "..."}` says a part of the read failed, and any other line is the script's own log. Print oldest first, and only what the script saw, never a guess. He reads the whole script when he applies the sensor.

A Chair that must see a state no signal gives makes a script sensor for its own chain with its own `create_sensor`; it writes the key `chain:<id>.sensor.<name>`, which only that Chair watches. It is not an event signal and has no door. A Chair whose chain lists `signals` and needs a number read after the chain ends (a key result's) opens the event signal itself with `create_event_signal` and asks for the standing sensor with `create_standing_sensor`: the sensor waits for an Apply, his or yours for him, as one you make does. A chain never needs you or him to make them: when a Chair asks, tell it to use its own tools.

## The GitLab and GitHub signals that ship with Remit

`gitlab` (`/hooks/gitlab`) and `github` (`/hooks/github`) are `builtin` in `list_event_signals`: the bundled plugins `gitlab` and `github` ship each with its rules as subscriptions, and they follow Remit as the built-in agents and playbooks do. Their subscriptions have Remit read the checks when a pipeline (a workflow run on GitHub) finishes on a commit a chain landed, and tell its Chair when one failed; the rest of what the forge posts is stored and does nothing until he subscribes to it. Each is the example to start from for another signal of its forge.

- GitLab sends the key as its Secret token. GitHub never sends it: it signs each post with the key (`X-Hub-Signature-256`), so on GitHub the key goes in the hook's Secret and the content type is `application/json`.
- GitHub names the event in a header and its kind in `body.action` (`header["X-Github-Event"] == "pull_request" && body.action == "closed"`); GitLab names it in `body.object_kind`.
- It follows Remit until he changes it. A change is made as for any signal (`update_event_signal`: start from `list_event_signals` and send back what stays); `edited` is then true and his version is kept through every restart.
- Each shipped subscription is `builtin` in `list_subscriptions` and is Remit's own. What he wants left out is a change to its `when` (`update_subscription`, e.g. `&& !body.project.path_with_namespace.startsWith('group/subgroup/')` on GitLab, since a project's path carries its group's, and `&& body.repository.full_name != 'owner/repo'` on GitHub); what he wants silenced is `pause_subscription`. A shipped one is never deleted. `edited` says it is his version, kept through every restart.
- `reset_event_signal` puts back what ships, when he asks: his note is replaced, so tell him what goes; its key, pause and sensors stay. A signal that does not ship has nothing to reset to.
- It is never deleted (`delete_event_signal` refuses it); to let nothing in he pauses it.
