# Record every decision the pipeline makes

Six families of event engines studied here (Grafana with Alertmanager, Temporal, Restate, Inngest with Trigger.dev and Hatchet, statecharts with Step Functions, and Home Assistant) all build the same shape. A cheap, pure evaluator runs inside the coordinator. Every outcome it reaches (fired, skipped, held, errored) is stored with a reason a machine can read. User I/O runs outside the coordinator under a deadline it must have, and a retry lifecycle ends in a visible paused state instead of a drop. Time is a stored due time owned by the entity it governs. The overlap policy is a named enum, and retention follows the slowest consumer. Remit breaks each of these rules. A firing error is only logged and retried forever (`internal/orch/signals.go:322-324`). A false `when` leaves no trace. A plugin `Process` call runs under the global `tickMu` with no timeout (`internal/orch/plugin_pipeline.go:244`, `internal/orch/schedule.go:67`). A cooldown hides which of three different loss policies it means. Retention deletes by age or count, only at start-up, without looking at any cursor. Remit is also ahead of every platform studied on two points. Its single SQLite writer gives exactly-once *recording* with no gossip or fencing. Its global-`seq` log makes a replay-based dry run and a cursor backfill cheap, and no platform here offers either. The recommended target keeps those strengths and adds a pure `Evaluate(sub, now, reading) → (sub, effects)`, a firing entity with a lifecycle, and a delivery stage outside the lock. The first change is a deadline on plugin `Process`, because one hung plugin stops every wake and admission today.

Coverage: five research notes (fetched 2026-11-05) plus `remit_current_state.md`, whose code citations were spot-checked for this report. `signals.go:322-324` shows the `default:` branch that only logs. `tell.go:49` refuses `len(p.Readings) != 1`. `plugin_pipeline.go:244` calls `p.o.runner.Process(ctx, ref, req)` with the tick's context. `schedule.go:67` takes `o.tickMu.Lock()`. `store/signal.go:133,197` hold the two forget queries, and neither reads `SeenSeq`. `signal.Probe(expr, reading, now)` exists at `internal/signal/probe.go:21`. `rg 'WithTimeout|WithDeadline'` over `internal/plugin/` and `plugin_pipeline.go`, tests excluded, returns nothing. The write paths, the duplicated checks and the rollup adapter were re-read for this report, and their `file:line` citations sit in the sections below. The Datadog note (`docs/research-datadog-signals.md`) bears on one point only, the "silent source" case (NoData). Every note left out the retention prior art that fits best. For this report, the Postgres replication-slot documentation and Kafka's introduction were read directly.

## Mature engines record why nothing happened

The deepest defect is that Remit decides things it never writes down. Every system studied treats a non-event as a fact worth storing, and each one shows a different part of the answer.

Grafana makes failure a *state*. A rule instance moves through Normal, Pending, Alerting, Recovering, **NoData and Error**. The author maps NoData and Error, per rule, to Error, Alerting, Normal or Keep last state. Every transition carries a `grafana_state_reason` (`No Data`, `Error`, `Paused`, `RuleDeleted`, `Updated`, `MissingSeries`) ([Grafana: state and health](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/state-and-health/); [NoData and Error](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/nodata-and-error-states/)). Grafana's history records each transition and ignores silences, so it shows what the rule *decided*, apart from what was *delivered* ([Grafana: state history](https://grafana.com/docs/grafana/latest/alerting/monitor-status/view-alert-state-history/)). Its blind spot matches Remit defect 2: a condition that stays false makes no transition and so leaves no record. Home Assistant fills that gap. It keeps the **last 5 run traces and a separate 5 "did not trigger" traces** per automation. Each trace stores the trigger, every condition result, the actions, the changed variables and "the configuration of the automation at the time it ran". A run that stopped names its cause: "Stopped because a condition failed", "Stopped on error", or "Stopped because only a single execution is allowed" ([HA: testing automations](https://www.home-assistant.io/docs/automation/testing/); [HA: troubleshooting](https://www.home-assistant.io/docs/automation/troubleshooting/)). The separate buffer matters, because near-misses would otherwise evict real runs.

Temporal and Restate turn failure into counters and lifecycles. A Temporal Schedule's describe output counts every way an action failed to happen: `overlap_skipped`, `missed_catchup_window` and `buffer_dropped`, next to the last ten actual and the next ten planned action times ([Temporal schedule proto](https://raw.githubusercontent.com/temporalio/api/master/temporal/api/schedule/v1/message.proto)). Temporal still finds unnamed skip paths in 2026. The Scheduler v2 rewrite merged on 2026-06-05 added a `buffer_expired` reason and a per-policy skip metric ([temporalio/temporal#10503](https://github.com/temporalio/temporal/pull/10503)). The lesson is to list every drop path, not just the obvious ones. Restate makes each unit of work a queryable row whose status runs `pending, scheduled, ready, running, paused, backing-off, suspended, completed`, with `retry_count`, `last_failure`, the failing command and `next_retry_at` ([Restate SQL introspection](https://docs.restate.dev/references/sql-introspection.md)). Its default retry policy (50 ms initial, factor 2, 60 s cap, **70 attempts, then pause**) has parked exhausted work instead of killing it since v1.6.0 (2026-01-30) ([Restate service configuration](https://docs.restate.dev/services/configuration.md); [v1.6.0](https://github.com/restatedev/restate/releases/tag/v1.6.0)). Temporal's `pause_on_failure` stops a schedule after a failed run and keeps a `notes` field for the reason ([Temporal: Schedule](https://docs.temporal.io/schedule)). Its Task Failures view flags a workflow after **five consecutive task failures**, because such a workflow "stays Running without making progress" ([Temporal Web UI](https://docs.temporal.io/web-ui)). Remit's errored firing is exactly that undetected loop.

Inngest closes the loop on the bus itself. After retries (0 to 20, default 4) are exhausted, a system event `inngest/function.failed` carrying `{error, event, function_id, run_id}` goes onto the same event stream, and any function can subscribe to it ([inngest/function.failed](https://www.inngest.com/docs/reference/system-events/inngest-function-failed)). SCXML has the same rule for conditions: a guard that errors counts as false *and* raises `error.execution` ([W3C SCXML §5.9.1](https://www.w3.org/TR/scxml/)). The counter-example is Hatchet, where "a failing filter expression means the filter does not match, so the run is not triggered" ([Hatchet CEL](https://docs.hatchet.run/v1/cel-expressions)). That is Remit's silent skip, offered as a feature. Restate's Kafka ingress shows how easily the gap reopens: a record the server rejects before acceptance leaves only a `LOG.warn` ([ingress-integration-kafka PartitionSession.kt](https://github.com/restatedev/ingress-integration-kafka/blob/4c20e3f/src/main/kotlin/dev/restate/integration/kafka/ingestion/PartitionSession.kt#L101-L207)).

For Remit this settles the shape of the fix. Every evaluation of a reading against a subscription ends in one outcome from a closed set: `fired`, `not_matched`, `condition_false`, `condition_error`, `held(reason)`, `skipped(cooldown|overlap|duplicate|paused)`, `failed(attempts, last_error)`. Firings and holds are durable rows. Near-misses go to a bounded per-subscription buffer, as in Home Assistant. A terminal failure is also appended to the log as a fact (`subscription.failed`), so the existing subscription machinery tells the Assistant and nothing new has to be built for alerting. This answers defects 1 and 2 directly. Defect 3 becomes visible at once, though it needs its own fix (next sections).

## No engine studied runs user I/O inside its matcher

Defect 4, a plugin `Process` under `tickMu` with no deadline, is the defect with the widest blast radius. It is also the one where the prior art agrees most. Inngest, Trigger.dev and Hatchet split the work in two. A non-Turing-complete matcher (CEL, chosen because it is "simple, fast, and not Turing complete") runs in the engine, and user code runs as a separate run with timeouts and retries ([Inngest: writing expressions](https://www.inngest.com/docs/guides/writing-expressions); [Hatchet CEL](https://docs.hatchet.run/v1/cel-expressions)). Temporal never runs I/O in the coordinator. The coordinator records "activity scheduled" and a timer, and a worker runs the activity elsewhere. **Temporal rejects an activity that has neither Start-To-Close nor Schedule-To-Close set**, and the server "relies on the Start-To-Close Timeout" to notice a dead worker at all ([Temporal: detecting activity failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures)). Grafana bounds each rule evaluation at **30 s and 3 attempts** and turns exhaustion into the Error state ([Grafana NoData and Error](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/nodata-and-error-states/)). When an evaluation runs slow, the newest tick wins, the older one is dropped, and the drop is counted in `grafana_alerting_schedule_rule_evaluations_missed_total{reason="slow_evaluation"}` ([grafana schedule.go](https://github.com/grafana/grafana/blob/main/pkg/services/ngalert/schedule/schedule.go)). Restate applies an inactivity timeout (1 min) and an abort timeout (10 min) to every handler ([Restate service configuration](https://docs.restate.dev/services/configuration.md)). AWS says to set `TimeoutSeconds` and `HeartbeatSeconds` for long-running work, and leaves them unset by default only for human-paced waits ([AWS Step Functions: Task state](https://docs.aws.amazon.com/step-functions/latest/dg/state-task.html)).

The fix comes in two steps, and the order matters. The first is a deadline on `runner.Process`, today: a `context.WithTimeout` at `plugin_pipeline.go:244` with a typed timeout error. That error then follows the failure path from the previous section. It is small and closes the outage. The second is structural: Temporal's command/event split. Under the lock, the tick evaluates, then writes the firing row and the cursor advance in one short transaction. A delivery stage outside `tickMu` picks up pending firings, runs the effect under its deadline, and takes the lock again only to commit the result. A hung plugin then costs one delivery slot, not the scheduler. Restate's Kafka consumer shows that this ordering is safe: **the offset advances once the record is durably accepted as an invocation, not when the handler succeeds**, and redelivery is dropped by dedup on the producer id and offset ([Restate ingress-kafka consumer_task.rs](https://github.com/restatedev/restate/blob/b074c52fe5264947c86c1a43c782db7cd2cd72bd/crates/ingress-kafka/src/consumer_task.rs#L702-L775)). Remit already has the dedup key, `(subscription, key, rev)` with `ON CONFLICT DO NOTHING`.

The same split fixes defect 9: `fireEnd`, `fireRun`, `pluginProcessing` and mark-live run their effects outside the firing transaction. Two schools disagree on what a crash between record and effect may cost. Akka runs side effects only after a successful persist, on "an at-most-once basis" ([Akka: Event Sourcing](https://doc.akka.io/libraries/akka-core/current/typed/persistence.html)). Alertmanager prefers "to send duplicate notifications rather than miss critical alerts" and makes duplicates harmless with idempotent receivers ([Alertmanager HA](https://prometheus.io/docs/alerting/latest/high_availability/)). For agent work, at-least-once with a key is the better choice. A missed wake is a silent failure, and a duplicate wake carrying the same firing key can be refused downstream. AGENTS.md already requires that a replayed call "does not act twice". So the firing key is passed into the effect as its request id, and each effect checks it.

Per-key serialization is the long-term answer to a single global lock. Restate runs at most one exclusive handler per object key, and Durable Entities run "operations serially" per entity ([Restate services](https://docs.restate.dev/foundations/services.md); [Durable entities](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-entities)). Restate also shows its cost: a paused invocation keeps its key's lock until it ends, so per-key order turns into per-key starvation unless the blocker shows as `sys_locks.acquired_by` ([Restate vqueues lib.rs](https://github.com/restatedev/restate/blob/b074c52fe5264947c86c1a43c782db7cd2cd72bd/crates/vqueues/src/lib.rs#L686-L790)). Remit's single SQLite writer makes the decision step cheap. Moving I/O off the lock removes the pressure, so per-key locking is the seam named in the ADR, not a change to build now.

## Overlap and time are named policies on one timer

Defect 3 is the clearest case of an implicit policy turning into a permanent stall. During a cooldown the core groups the held readings. `fireTell` refuses more than one reading (`tell.go:49`). The refusal falls into the log-only `default` branch. The group never shrinks, so the subscription is stuck for good. The root cause is a concept with two owners. The core decides that a cooldown *collapses* readings, and each processor decides on its own how many readings it accepts. The `len(p.Readings) != 1` check now appears in six processors: `tell.go:49`, `chain_jobs.go:20`, `assist.go:34`, `hire.go:59`, `teach_memory.go:37` and `start_event.go:19`. Inngest names the policies a cooldown could mean, and they differ in what gets lost. **Rate limit "skips excess triggers"**, throttle delays starts and drops nothing, and debounce collapses a burst into one run with "the last event in the burst". Debounce takes an optional `timeout`, because otherwise a source that never goes quiet never fires ([Inngest flow control](https://www.inngest.com/docs/guides/flow-control); [Inngest debounce](https://www.inngest.com/docs/guides/debounce)). Inngest fixes the order these controls apply in (rate limit, then batching, then debounce or singleton, then step concurrency), and **registration fails** when two controls cannot be combined, such as singleton with batching ([Inngest singleton](https://www.inngest.com/docs/guides/singleton)). That registration check is the missing guard. Remit lets an agent create a cooldown subscription with a tell action, a pair that can never succeed.

Overlap for runs, as distinct from readings, has an equally rich vocabulary. Temporal Schedules name six policies: **Skip (default), BufferOne, BufferAll, CancelOther, TerminateOther, AllowAll**. A catchup window (default one year, minimum 10 s) decides how late a missed action may still run ([Temporal: Schedule](https://docs.temporal.io/schedule)). Home Assistant names four modes (single, restart, queued, parallel), with `max` defaulting to 10 and a logged overflow outcome ([HA: automation modes](https://www.home-assistant.io/docs/automation/modes/)). Hatchet gives three strategies per CEL key: GROUP_ROUND_ROBIN, CANCEL_IN_PROGRESS and CANCEL_NEWEST ([Hatchet concurrency](https://docs.hatchet.run/home/concurrency)). Remit's routine "runs one at a time and catches up once", which is Temporal's BufferOne under another name. It should carry that name as an enum value, with a counter for each skip. Alertmanager supplies the repeat rule: a group is re-sent only if its firing set changed, its resolved set changed, or `repeat_interval` (default 4h) elapsed. Otherwise the send is suppressed by the dedup stage, and that stage is named ([Alertmanager configuration](https://prometheus.io/docs/alerting/latest/configuration/); [Alertmanager HA](https://prometheus.io/docs/alerting/latest/high_availability/)). Grafana's pending period and keep-firing-for are debounce on entry and on exit, measured against the evaluation clock. Re-entering Alerting from Recovering sends no new notification ([Grafana: alert rule evaluation](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/)).

On time itself the notes show a real trade-off. The Inngest researcher points out that Remit's clock-as-readings is *more* inspectable than Inngest's cron, which carries no event at all. Temporal, Restate, Durable Entities and Harel's statecharts all go the other way and keep one timer primitive, owned by the entity, with everything else built from it. Harel models cooldown and deadline as lower and upper bounds Δt1 < Δt2 on a state ([Harel 1987](https://www.state-machine.com/doc/Harel87.pdf)). Restate v1.8 turned delayed calls into queue entries with a run-at time, where they had been separate timers ([Restate state_machine mod.rs](https://github.com/restatedev/restate/blob/b074c52fe5264947c86c1a43c782db7cd2cd72bd/crates/worker/src/partition/state_machine/mod.rs#L1020-L1040)). The decisive evidence is what happens to timers kept in memory. An XState 5.33.3 actor restored from a persisted snapshot came back **without its pending `after` timer and stayed in `cooling` indefinitely**. The snapshot has no scheduler key, and even a re-armed timer would wait its full delay, because `startedAt` is never read ([xstate system.ts](https://github.com/statelyai/xstate/blob/main/packages/core/src/system.ts); reproduced in the state-machines note). Home Assistant's own documentation says a restart loses "any delay, wait, or trigger duration in progress" ([HA: automation modes](https://www.home-assistant.io/docs/automation/modes/)). Temporal timers, stored on the server, fire late after an outage and never vanish ([Temporal: timers](https://docs.temporal.io/workflow-execution/timers-delays)). The two readings of the evidence fit together. Time belongs in a stored `due_at` on the subscription or routine, which the tick compares with `now`. A tick that causes a firing is still recorded, as the firing's cause, so inspection survives. The private 1:1 `clock:<subid>` sensor, and the four predicates that tell routines, check-backs, watches and automations apart, then have no job left. Shared clock signals other subscriptions match on can stay readings.

The statecharts note gives one more reason to make the model explicit. A subscription has at least three independent aspects: control (active, paused, ended), health (ok, held(reason)) and window (idle, cooling(until), due(at)). Flattened into fields, these give 18 combinations. That is the state-explosion condition Harel named ([statecharts.dev: state explosion](https://statecharts.dev/state-machine-state-explosion.html)). Akka dropped its dedicated `PersistentFSM` in favour of a plain entity whose command handler is chosen by state ([Akka API: persistence.fsm](https://doc.akka.io/japi/akka/current/akka/persistence/fsm/package-summary.html)). That suggests three small Go enums and a transition function, not a statechart library.

## State and stream need their own start points and retention

The word "signal" covers both a current value (keep newest N) and an event stream (keep by time), and four defects follow from that. Every platform keeps the two apart. Temporal has Query (read state, writes no history) beside Signal (an event written to history) ([Temporal message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing)). Restate keeps per-key K/V state, one-shot promises and multi-shot signals as three separate things ([Restate external events](https://docs.restate.dev/develop/ts/external-events.md)). Alertmanager treats state as a lease: clients "re-send firing alerts at regular intervals", an alert left without `endsAt` expires after `resolve_timeout` (5m), and "alerts themselves are not persisted" because the source re-asserts them ([alerts_api.md](https://github.com/prometheus/alertmanager/blob/main/docs/alerts_api.md); [Alertmanager HA](https://prometheus.io/docs/alerting/latest/high_availability/)). Home Assistant's triggers fire on edges only, and its docs keep warning about the result: a door already open when the automation is saved never fires ([HA: triggers](https://www.home-assistant.io/docs/automation/trigger/)). A signal must declare `kind: state | stream`. A state signal keeps its newest values, can be re-derived, and offers "evaluate the current value on subscribe". A stream signal keeps occurrences until every live cursor has passed them. The Datadog note's `body.no_data` on a silent app is Grafana's NoData case. A state signal whose source stops asserting should go to a NoData outcome, not just keep its stale last value.

Defect 7 is a start-position defect. A Chair's wildcard watch created later starts at `SeenSeq=0` and hears all of history, while other creators copy `LastSeq` in three places. The prior art makes the start point an explicit choice at the boundary. Restate takes Kafka's `auto.offset.reset` or a consumer group's committed offset ([Restate Kafka](https://docs.restate.dev/services/invocation/kafka.md)). Temporal backfill takes a half-open range with its own overlap override ([Temporal: Schedule](https://docs.temporal.io/schedule)). Hatchet's one-minute *lookback* on event waits admits that forward-only waits race with arrival ([Hatchet durable event waits](https://docs.hatchet.run/llms/v1/durable-event-waits.md)). With a global `seq`, Remit can state this exactly: `start: now | seq N | time T | current` becomes a required field of the one create path, and the three copies go. Grafana's "editing a rule resets its instances to Normal" adds the rule for edits: a changed condition is a new revision with a fresh, explicit start ([Grafana: alert rule evaluation](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/)).

Defect 5 is retention that ignores cursors. `ForgetEventReadings` deletes by time and keeps the newest of each key, because a revision counts on from the newest (its own comment, `store/signal.go:128-133`). `ForgetReadings` keeps the newest N. Neither reads `SeenSeq`, and both run only at start-up. Temporal's Workflow Streams shows the failure in plain terms: after truncation, "a subscriber behind the new base is advanced silently, so it may re-receive items" ([Temporal Workflow Streams](https://docs.temporal.io/workflow-streams)). Inngest bounds replay by the billing plan's retention, which is 24 hours on Free ([Inngest replay](https://www.inngest.com/docs/platform/replay); [Inngest limits](https://www.inngest.com/docs-markdown/usage-limits/inngest)). Restate trims its log only after a snapshot covering the entries is durable, and keeps dedup retention as a separate knob ([Restate architecture](https://docs.restate.dev/references/architecture.md)). Alertmanager clamps `repeat_interval` to `--data.retention` (120h) and garbage-collects every 15 minutes ([alertmanager main.go](https://github.com/prometheus/alertmanager/blob/main/cmd/alertmanager/main.go)). The two classic logs take opposite sides. In Kafka, "events are not deleted after consumption". A per-topic setting says "for how long Kafka should retain your events", "after which old events will be discarded", so retention is set by time per topic, not by consumer position ([Kafka introduction](https://raw.githubusercontent.com/apache/kafka/trunk/docs/getting-started/introduction.md)). Postgres replication slots hold WAL for the slowest consumer. With `max_slot_wal_keep_size` at `-1`, the default, "replication slots may retain an unlimited amount of WAL files". When a cap is set and a slot falls behind it, the standby "may no longer be able to continue replication", and the loss shows in `pg_replication_slots`. `idle_replication_slot_timeout` (default 0, off) invalidates idle slots ([PostgreSQL: replication settings](https://www.postgresql.org/docs/current/runtime-config-replication.html)). Remit's subscriptions are cursors that must not lose readings, so the Postgres model fits. A stream's floor is `min(SeenSeq)` over live subscriptions, with no age cap by default. Assumption: no default age cap, because AGENTS.md says Remit "caps none" and Postgres also defaults to unlimited. The cap is a hardening seam: an optional setting under the ADR's *Revisit when*. Once one is set, a subscription that falls past it goes to `held(cursor_expired)` with the gap recorded, as a Postgres slot is invalidated visibly, and is never advanced silently. An ended subscription releases the floor at once. A paused or held one keeps holding it, so a resume loses nothing, and the Subscriptions tab shows how many readings it holds back, the way `pg_replication_slots` shows what a slot retains. Retention runs on a timer, not at start-up, and facts are a stream like any other. Firing records outlive the longest cooldown and dedup window, because Trigger.dev's 30-day TTL shows that a dedup key forgotten too early fires again ([Trigger.dev idempotency](https://trigger.dev/docs/idempotency)).

Defects 6 and 8 come from having five write paths and three triggers instead of one door. Restate's principle is that "events get always added to the log first, and once they are received by the processor they are acted upon" ([Restate blog](https://www.restate.dev/blog/building-a-modern-durable-execution-engine-from-first-principles)). Grafana draws the line pause must respect: pausing a rule stops evaluation, which is "different from mute timings", where evaluation continues and delivery stops ([Grafana: create rule](https://grafana.com/docs/grafana/latest/alerting/alerting-rules/create-grafana-managed-rule/)). The code shows where the pause leaks. `Orchestrator.Emit` (`event.go:72`) refuses a paused event signal (`event.go:95-96`, `ErrEventSignalPaused`, "whoever writes it"). The private `emit` (`signals.go:62-83`) stores and judges with no signal-pause check. A plugin sensor's readings go through `emit` (`plugin_pipeline.go:224`), and the guard before it (`plugin_pipeline.go:206`) checks only whether the *sensor* is paused. The same `emit` serves script sensors (`sensor.go:229`) and rollup (`rollup.go:95`). `emitTransient` routes clock and transient readings without storing them (`signals.go:94-110`). Facts and chain records call `tx.AddReading` in their caller's transaction at five sites: `assist.go:27`, `lifecycle.go:97`, `check_review.go:73`, `teach.go:82` and `signals.go:474` (inside `putSignals`, which `commit.go:124` calls). `teach.go:82` was added after the internal code map was made. `Emit`'s own write is `event.go:109`, and `emit`'s is `signals.go:72`. That adds up to several ways in, and each one decides pause, timestamp and dedup on its own. One ingest function, which parses, assigns identity, applies pause and dedups, removes the defect by construction. Dedup there follows Inngest: a duplicate "is still stored, but no new run executes" ([Inngest events](https://www.inngest.com/docs/events)). A unique-index conflict therefore counts as a recorded duplicate, not an error that silences the sensor. A transient reading's identity comes from the producer (a delivery id, or the scheduled time, as Temporal uses `scheduled_time` as the identity of a scheduled run), never from an `At` left unset ([Temporal schedule proto](https://raw.githubusercontent.com/temporalio/api/master/temporal/api/schedule/v1/message.proto)).

## A dry run on the live evaluator is Remit's unclaimed edge

Agents create and debug Remit subscriptions, and the prior art for agent-grade tooling is recent and specific. Restate v1.8.0 (2026-10-14) rebuilt its CLI "for scripts, CI and AI agents", with `--json`, structured errors with distinct exit codes, and a shared `--dry-run`/`--yes` preview-then-apply flow on every changing command ([Restate v1.8.0](https://github.com/restatedev/restate/releases/tag/v1.8.0)). Step Functions' TestState runs one state's definition against an input without creating a state machine. It returns `status`, `nextState` and the intermediate `inspectionData`, and since November 2025 it can mock service results ([AWS TestState](https://docs.aws.amazon.com/step-functions/latest/dg/test-state-isolation.html)). Hatchet's CEL `debug` evaluates an expression on the engine against a sample ([Hatchet CEL](https://docs.hatchet.run/v1/cel-expressions)). Grafana's Preview evaluates "at this moment" and skips NoData and Error handling ([Grafana v8.5 docs](https://grafana.com/docs/grafana/v8.5/alerting/unified-alerting/alerting-rules/index.xml)). **None of the platforms studied runs a new consumer over past events.** Inngest and Trigger.dev replay *runs*, and Trigger.dev defaults to the last 7 days ([Trigger.dev bulk actions](https://trigger.dev/docs/runs/bulk-actions)).

Remit holds both pieces those systems lack. It has a durable local log with a global `seq`, and `signal.Probe(expr, reading, now)` already takes time as an input (`internal/signal/probe.go:21`). Determinism is what makes replay valid: Temporal forbids reading the clock inline for exactly this reason ([Temporal: workflow definition](https://docs.temporal.io/workflow-definition)). Once evaluation is the pure function the statecharts note describes (XState's `transition(machine, state, event)` returns `[nextState, actions]` and "captures these actions but doesn't execute them", [Stately: pure transitions](https://stately.ai/docs/pure-transitions)), three things share one code path. The dry run is the evaluator over `(N..head]` with effects returned and not run. Backfill is the same loop with effects run, kept idempotent by the firing key. `explain_subscription(sub, reading)` is a single step of the loop. ADR-0045 already gates a measure's Apply on a `signal.Probe` dry run, so the subscription dry run extends a rule the codebase holds rather than adding a concept. The result goes to agents as data: "would fire 4 times at seqs [...], skip 9 for cooldown, error 1 on `body.x` missing".

Two further patterns finish the tool surface. Temporal's Update validator rejects a write "before the Update is written to history" ([Temporal Go message passing](https://docs.temporal.io/develop/go/message-passing)). That is the place to refuse the cooldown-plus-tell pair, an unknown processor (the case behind defect 1), and an unparsable CEL expression, with the reason returned to the agent at once. Temporal Scheduler v2 resolves the policy and stores it on each buffered start, so a later edit does not rewrite queued work ([temporalio/temporal#10503](https://github.com/temporalio/temporal/pull/10503)). Step Functions Express loses older executions' graphs because it does not store definitions ([AWS: execution details](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-view-execution-details.html)). So each firing and trace records the subscription revision and the policy it was decided under, which Home Assistant does with "the configuration at the time it ran".

## Target design: evaluate, record, then deliver

The pipeline has six stages, each with one owner. **Ingest** is the one door every producer calls (door, CLI, poll, script, plugin Sense and Process emits, facts, chain records, clock). It parses once, takes identity from the producer, applies pause, records duplicates as duplicates, and appends to the log in the caller's transaction, which keeps today's transactional-outbox property. **The log** holds readings with a global `seq`, in signals that declare `kind: state | stream`. **Evaluate** is the pure core: `Evaluate(sub, now, reading | tick) → (sub', []Effect)`. Its `Effect` is a closed sum: `Fire{action, key, rev, policy}`, `Skip{reason}`, `Hold{reason}`, `Schedule{due_at}`, `Advance{seq}`. It applies a fixed, documented order: key match, condition, start position, pause, flow policy, overlap, dedup. It runs under `tickMu` and touches no I/O. **Record** is one short transaction per subscription and pass. It writes firings with their frozen revision and policy, near-miss outcomes into the bounded buffer, the cursor, and the lifecycle state, which has three small enums (control, health, window) and a `due_at`. **Deliver** runs outside the lock. Workers take pending firings, run each effect under a deadline it must have, pass the firing key as the request id, retry with backoff, and commit the result or failure in a short transaction. Exhaustion, or a non-retryable error, moves the firing to `failed`, holds the subscription with a note saying who and why, and appends `subscription.failed`. **Retention** runs periodically. It trims streams below the lowest live cursor up to an age cap, holds laggards with the gap recorded, and keeps firing rows past the longest window.

Routines become Schedule-shaped: a spec, an overlap enum (BufferOne as today's default, by name), a catchup window, pause with notes, and counters for every skip. Their time lives in `due_at`, and the private clock sensors go. Rollup turns out not to be a derived signal. `rollup.go:19-31` describes an HTTP poll (`GET {url}/rollups/{name}`, behind the `-telemetry-rollups` flag) against the owner's telemetry store, with a contract "assumed, since the store is not built". `docs/telemetry-store/README.md` agrees: "Nothing is built". The adapter runs its own scheduling. `pollRollups` (`rollup.go:55-74`) claims each watched key once per `rollupEvery` (1 minute, `rollup.go:34`) and reads it in `o.background`, outside `tickMu`. Each read has its own 10 s `rollupTimeout` (`rollup.go:36`), and each result feeds its own silence count (`rollups.result`, `rollup.go:83`; `rollupSilence`, `rollup.go:45-51`). After every stored reading it trims the key to `rollupReadingsKept` = 1000 (`rollup.go:38,98`). That makes rollup the one signal whose retention runs while the server is up, again by count, not by cursor. It reaches the log through the private `emit` (`rollup.go:95`), which takes `tickMu`, next to the `Sensor` model's poll kind, which already carries `Source`, `Query`, `EveryMinutes` and `Cursor` (`model/sensor.go:44-55`). So Grafana recording rules are the wrong model for it. The target is a poll sensor on a `telemetry` source, with one scheduler and one silence rule, or no rollup until the store exists. Choosing between those is the owner's call, because the telemetry store's own plan decides it. The agent surface is `create/change_subscription` with a validator and `--dry-run` semantics, `explain_subscription(sub, reading)`, `dry_run_subscription(sub, from)`, `describe_subscription` (cursor vs head, current lifecycle per aspect, next `due_at`, last firing, last failure with attempt and next retry, recent near-misses, counters), and `resume`/`skip`/`retry_now` with a reason. On screen, holds, failures and near-misses appear on the Subscriptions tab and count toward what waits for the owner. This crosses storage, a rail-adjacent effect path and the agent tools. AGENTS.md routes such a change through `aio-architect-advisor` to an ADR that supersedes the affected parts of ADR-0049. Per-key serialization, delivery concurrency limits and plugin heartbeats go under *Revisit when*.

## Conclusion

The prior art moves the question away from "which engine should Remit resemble". Each engine treats a decision it never recorded as a defect, and each spent years closing paths it had missed: Grafana's Recovering state in v12, Restate's pause-by-default in v1.6, Temporal's `buffer_expired` in 2026. Remit can skip that slow accretion. Make the evaluator pure and the outcome set closed, so an unrecorded path cannot exist. Then every later feature (dry run, backfill, explain, retention floor) is a different driver over the same function and the same rows. The single SQLite writer, often seen as a scaling limit, is what makes this cheap. Exactly-once recording leaves only one hard problem, a crash between record and effect, and a firing key passed into the effect answers it.

The second lesson cuts against an internal instinct: "dead letter and move on" is the wrong end state for a failing subscription. Restate and Temporal both park failing work and keep its position, because a cursor that stays at the failed reading can be resumed after the fix. Cursor-aware retention (change 9) is what makes parking safe. That ties together two changes that look independent: retention has to know about cursors before hold-on-failure can be trusted to lose nothing.
