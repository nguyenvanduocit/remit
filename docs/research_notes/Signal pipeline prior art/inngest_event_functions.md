# Event-driven durable function platforms: Inngest, with Trigger.dev and Hatchet for contrast

Scope note: researched 2026-11-05 from the official docs (inngest.com/docs, trigger.dev/docs, docs.hatchet.run) and the `inngest/expr` GitHub repo, plus a read of the Remit signal code for two inferences. 44 tool calls; the calls past the 15-call guideline closed gaps a first pass left open (debounce semantics, plan limits, Trigger.dev concurrency, TTL and bulk replay, Hatchet lookback waits and or groups, the code checks). The pages were read through a summarizing fetch tool, so short quotes are as the tool reported them. Mapping labels (a)-(g) refer to the Remit open problems: (a) silent fail/skip, (b) no start position/backfill/dry-run, (c) retention ignores cursors, (d) signal conflates state and stream, (e) time split between clock sensors and windows, overlap policy implicit, (f) plugin processor under global lock with no timeout, (g) AI agents create and debug subscriptions through tools.

## 1. Inngest triggers: event name, wildcard, `if` (CEL), cron; event envelope; idempotency by id

### Takeaway
An Inngest function declares up to 10 triggers: an event name (wildcards allowed only after `/` or `.`), an optional CEL `if` filter on that event, or a cron string with an optional TZ. The envelope is `{name, data, id?, ts?, v?}`. An `id` dedupes for 24 hours across all event types, and the duplicate is still stored. One event fans out to every matching function.

### Cited Findings
- The `if` filter is CEL: "Expressions are defined using the Common Expression Language (CEL) with the original event accessible using dot-notation," e.g. `'event.data.action == "published"'`. Confirmed. — [Inngest create function reference](https://www.inngest.com/docs/reference/functions/create)
- CEL was chosen because it is "simple, fast, and not Turing complete," which lets Inngest evaluate millions of expressions at scale. Only a subset of CEL helpers/macros is supported, and `in` is unsupported in `if` expressions (use `==` chained with `||`). — [Writing expressions](https://www.inngest.com/docs/guides/writing-expressions); [waitForEvent reference](https://www.inngest.com/docs/reference/functions/step-wait-for-event)
- A function can combine up to 10 triggers. "Cron triggers with overlapping schedules for a single function will be deduplicated." Cron functions receive no `event` argument. Cron syntax allows a timezone prefix: `TZ=Europe/Paris 0 12 * * 5`. — [create reference](https://www.inngest.com/docs/reference/functions/create)
- Wildcards: `app/*` matches every event whose name starts with `app/`. A wildcard must follow `/` or `.` and cannot appear mid-pattern (`app/user.update*` is unsupported). Wildcard triggers cannot carry a schema because matched payloads differ. The docs advise inspecting `event.name` and validating each payload in the handler. — [Multiple triggers & wildcards](https://www.inngest.com/docs-markdown/guides/multiple-triggers); [Trigger helpers (TS v4)](https://www.inngest.com/docs/reference/typescript/v4/functions/triggers)
- Envelope: `name` and `data` are required. `ts` is Unix ms and defaults to receive time. `v` is a payload version string (e.g. `"2024-01-14.1"`) used "to track changes in the event payload shape over time." No top-level `user` field was found in the current format; user info goes inside `data`. — [Event payload format](https://www.inngest.com/docs/features/events-triggers/event-format)
- Idempotency by id: "When an event is sent again with the same `id` within 24 hours, the event is still stored, but no new run executes." "The `id` is global across all event types," so the docs recommend prefixing with the type, e.g. `item-imported-9f08sdh84`. — [Events](https://www.inngest.com/docs/events)
- Function-level `idempotency` is a CEL key expression. It "prevents duplicate events from triggering the function more than once in 24 hours" and is "equivalent to a rateLimit with a key, limit of 1, and 24h period." — [create reference](https://www.inngest.com/docs/reference/functions/create)
- Fan-out: "One event may start several functions." The docs contrast this with a queue: "every function that matches the event runs." — [Events](https://www.inngest.com/docs/events)
- Naming convention in examples: `namespace/noun.verb`, e.g. `billing/invoice.paid`, `app/user.signup`. The `inngest/` prefix is reserved for system events. — [Events](https://www.inngest.com/docs/events); [inngest/function.failed](https://www.inngest.com/docs/reference/system-events/inngest-function-failed)

### Inferences
- Inngest has two separate dedupe layers. Event-level dedupe (by `id`, global, 24h) stores the event but suppresses runs. Function-level dedupe (by a key expression, per function, 24h) is a rate limit. Remit keys firings by (subscription, key, revision), which corresponds to the function-level layer and is stronger: it has no time window, so it is permanent. Inngest's "still stored, no new run" is the shape to copy for (a): the duplicate reading exists and can be shown with a reason, so it never vanishes.
- The `v` field addresses (d) indirectly: a stream reading carries its schema version, so an agent debugging a CEL condition (g) can tell when a payload shape changed under it.
- Wildcards restricted to segment boundaries (`/`, `.`) make key patterns index-friendly: they work as prefix matches on a segment tree. This is a cheap rule to copy for Remit's key patterns.
- Cron is a trigger kind on the function, not a separate sensor that emits readings. That is one data point for (e). Remit's design, where the clock is a source that appends readings, has the advantage that ticks are replayable and visible in the log; Inngest's cron runs carry no event at all.

### Gaps
- No official source was found for a top-level `user` envelope field in current docs. It existed in older Inngest SDKs as far as I recall (unverified, not stated as fact).
- Exact limits (payload size, max events per send) were not fetched.

## 2. Inngest flow control: concurrency, throttle, rate limit, debounce, batching, priority, singleton

### Takeaway
Each control answers a different question. Rate limit and idempotency **drop**. Throttle **delays** starts and drops nothing. Debounce **collapses** a burst into one run with the last event. Batching **groups** events. Concurrency **caps executing steps** and holds nothing for sleeping or waiting runs. Priority **reorders**. Singleton allows **one active run per key** and chooses `skip` or `cancel` for newcomers. They apply in a documented order: rate limit → batching → debounce/singleton → step concurrency.

### Cited Findings
- **Concurrency**: limits concurrently running *steps*, not runs: it "caps steps executing at the same time," and runs that are waiting do not take a slot. A key is a CEL expression. Scope is `fn` (default), `env`, or `account`; `env` and `account` require a key and share it across functions. — [Flow control guide](https://www.inngest.com/docs/guides/flow-control); [create reference](https://www.inngest.com/docs/reference/functions/create)
- **Throttle**: limits how many new runs *start* per period, with `limit`, `period`, `burst` and optional `key`. "Extra runs wait in the queue." Nothing is dropped. — [Flow control guide](https://www.inngest.com/docs/guides/flow-control); [create reference](https://www.inngest.com/docs/reference/functions/create)
- **Rate limit**: "skips excess triggers." Use it "when you can discard excess work." The period is 1s–60s with an optional key. "The period begins when the first matching event is received." — [Flow control guide](https://www.inngest.com/docs/guides/flow-control); [create reference](https://www.inngest.com/docs/reference/functions/create)
- **Debounce**: "waits for a quiet period so a burst of updates starts one run." The period is 1s–7d with an optional key. — [Flow control guide](https://www.inngest.com/docs/guides/flow-control); [create reference](https://www.inngest.com/docs/reference/functions/create)
- **Batching** (`batchEvents`): `maxSize` up to 100, `timeout` 1s–60s, optional `key` and `if`. The handler receives `events[]`. Batching is incompatible with rate limiting and priority, and batched items skip the scheduling controls (debounce, singleton). — [create reference](https://www.inngest.com/docs/reference/functions/create); [Flow control guide](https://www.inngest.com/docs/guides/flow-control)
- **Priority**: an expression returning an integer in -600..600 by default; higher runs first. It reorders and drops nothing. It cannot be combined with batching or rate limiting. — [create reference](https://www.inngest.com/docs/reference/functions/create); [Flow control guide](https://www.inngest.com/docs/guides/flow-control)
- **Singleton**: "applies to the entire function run for that key." The key is a required CEL expression. Mode `skip` discards the new event and lets the active run continue. Mode `cancel` cancels the active run and starts a new one; completed steps are not undone, an executing `step.run` finishes first, and in rapid bursts some new runs may be skipped rather than cancel each prior run. A retrying run keeps its slot. Singleton is incompatible with batching ("registration fails"). — [Singleton guide](https://www.inngest.com/docs/guides/singleton)
- Singleton differs from concurrency 1: concurrency 1 governs only step execution, so it "does not enforce the same run-level behavior." — [Singleton guide](https://www.inngest.com/docs/guides/singleton)
- Processing order: rate limiting first (skip excess), then batching, then debounce and singleton (scheduling), then step concurrency (execution). — [Flow control guide](https://www.inngest.com/docs/guides/flow-control)
- Run timeouts: `timeouts.start` cancels a run that waits too long to begin. `timeouts.finish` cancels a run that executes too long, not counting start wait. — [create reference](https://www.inngest.com/docs/reference/functions/create)

### Inferences
- Mapping to Remit's **cooldown window**: a cooldown that drops firings inside the window is Inngest's **rate limit with limit 1** (or `idempotency` with a short period). A cooldown that delays them is **throttle**. A cooldown that waits for quiet and then fires once with the latest reading is **debounce**. Remit's cooldown is one knob that hides which of the three it means. That is the "overlap policy implicit" half of (e). The lesson: name the policy as an enum (`drop | delay | collapse`), because each has different loss semantics that an agent must be able to read (g).
- Mapping to **"one run at a time"**: Inngest separates *run-level* exclusivity (singleton skip/cancel) from *execution-level* throttling (concurrency on steps, which excludes waiting runs). "Start or wake a work chain" in Remit is run-level, so singleton is the right model: an explicit `skip | cancel` (and Hatchet adds "queue", see §7) per key, where the key is a CEL expression over the reading. A retrying run holding its slot is a detail worth copying.
- Every drop path (rate limit, idempotency, singleton skip, debounce superseded) is a decision. For (a), Remit should record each non-firing as a row with its reason, e.g. `skipped: cooldown`, `skipped: singleton`, `collapsed into firing X`, so "why didn't it run" has an answer.
- `timeouts.start`/`finish` correspond to Remit's deadline window and to (f): a processor needs a `finish` timeout enforced outside the processor.
- The documented processing order is a design artifact worth copying: Remit should fix and document the order in which condition, cooldown, dedupe and one-at-a-time are evaluated, so the outcome of a reading is deterministic and explainable.

### Debounce detail
- Debounce delivers the **last** event: "The handler receives the last event in the burst, not the first event and not an array of every event." The first matching event starts the period, and each later match restarts the wait and replaces the pending event. An optional `timeout` caps the total delay: once it passes, the function runs with the latest event, and a later event starts a new period. `key` is a CEL expression, with one period per key value. — [Debounce guide](https://www.inngest.com/docs/guides/debounce)
- Inference: a Remit "collapse" cooldown needs both a quiet period and a max wait. Without a max wait, a source that never goes quiet never fires, which is a silent skip (a).

### Gaps
- Whether rate-limited or singleton-skipped events appear in the dashboard with a reason was not found in the fetched pages (see §5).

## 3. Durable waits: step.waitForEvent (`match`/`if`, timeout), step.sleep, cancelOn, and how matching is indexed

### Takeaway
A run pauses on `waitForEvent(name, {match | if, timeout})` and resumes with the first later event that matches, or with `null` on timeout. `match` is a field-equality shorthand. `if` is CEL over `event` (the trigger) and `async` (the awaited event). `cancelOn` uses the same matcher to cancel a running or sleeping run. Inngest scales the matching with `inngest/expr`, an aggregate expression engine that turns O(n²) matching into roughly O(n) by indexing the lifted literals of conjunctive comparators.

### Cited Findings
- Signature: `step.waitForEvent(id, {event, timeout, match | if})` returns `Promise<null | EventPayload>`. The step `id` memoizes state across function versions. — [waitForEvent reference](https://www.inngest.com/docs/reference/functions/step-wait-for-event)
- `match`: a dot path such as `data.invoiceId` that "must be equal on the trigger event and the awaited event." `if` is a CEL expression where `event` is the original trigger and `async` is the awaited event, e.g. `event.data.userId == async.data.userId`. The two "cannot be combined." — [waitForEvent reference](https://www.inngest.com/docs/reference/functions/step-wait-for-event)
- `timeout` accepts a duration string, milliseconds, a Date, or a Temporal absolute instant. The `null` result on timeout is implied by the return type, not stated in prose. — [waitForEvent reference](https://www.inngest.com/docs/reference/functions/step-wait-for-event)
- In `group.parallel()`, "a losing step.waitForEvent() is not cancelled." It stays paused until its timeout and keeps the run in Running state. — [waitForEvent reference](https://www.inngest.com/docs/reference/functions/step-wait-for-event)
- `cancelOn`: entries take an event, a `match` path or an `if` expression (not both), and a `timeout`, to "cancel a running or sleeping function." — [create reference](https://www.inngest.com/docs/reference/functions/create)
- `inngest/expr`: "turning O(n^2) expression matching into O(n)." It parses each expression, lifts literals, breaks expressions into subgroups of `&&` comparators, stores each group's comparator in a matching engine, and per event filters to a subset that is "almost always matching." Source files suggest per-type engines (`engine_stringbtree.go`, `engine_stringmap.go`, `engine_number.go`, `engine_null.go`); that is inferred from file names, not documented. — [github.com/inngest/expr](https://github.com/inngest/expr)

### Inferences
- The doc does not say whether an event that arrived *before* the wait started can satisfy it. By design and by the docs' silence, Inngest waits are forward-only. For Remit this is the stream-vs-state split in (d). A wait on a **stream** must start at a cursor (the seq at wait start, or an explicit earlier seq). A wait on **state** ("until CI is green") should first check the current value. Remit can do better than Inngest here because its log has a global seq: a wait records `from_seq` and can be satisfied by any reading after it, which closes the race between "wait registered" and "event arrived".
- Indexing lesson for Remit at its scale: with one SQLite log and tens to hundreds of subscriptions, O(n) CEL evaluation per reading is fine. Copy the *shape*: (1) a cheap prefilter on key pattern (segment index), (2) full CEL evaluation on candidates. Restricting conditions to aggregatable forms is not needed yet.
- Matching on `event` vs `async` (trigger vs awaited) is a clear naming convention for (g). An agent writing a wait condition sees two named variables, not one ambiguous `reading`.
- `cancelOn` corresponds to a subscription whose action is "stop/cancel chain". Inngest makes cancellation part of the *function's* declaration rather than a separate subscription. A design option for Remit is to let a chain's wait or lifecycle declare its own cancel predicates, so they die with the chain and leave no orphaned subscriptions.

### Gaps
- No Inngest engineering blog post on waitForEvent matching internals was found in the search; only the `inngest/expr` README. How pauses are stored (per event name with a CEL-indexed lookup) is not documented in what was fetched.
- `step.sleep`/`sleepUntil` pages were not fetched. Their semantics (durable timer, no compute while sleeping) are standard but uncited here.

## 4. Replay, bulk replay, backfill, and dry runs

### Takeaway
Inngest Replay re-runs selected runs of one function over a time range filtered by status (including **Skipped**, for events that arrived while the function was paused), after you deploy the fix. It creates new executions, so side effects repeat unless idempotent. History is bounded by the plan's event retention. No documented feature runs a *new* function over past events (backfill). Dry runs happen in the local Dev Server, by sending test events, and in the webhook transform preview.

### Cited Findings
- Replay selects runs by function, time range and status, and you review the selection before starting. "Include successful runs only if they also need recovery." For a paused function, select the **Skipped** status after resuming it to replay events that arrived while paused. — [Replay](https://www.inngest.com/docs/platform/replay)
- Replay "creates new executions, so check which charges, messages, or records could repeat." It "spreads the selected work over time." Single runs use "Rerun a run." — [Replay](https://www.inngest.com/docs/platform/replay)
- Historical availability "depends on your plan's event retention." — [Replay](https://www.inngest.com/docs/platform/replay)
- Backfill of a new function over past events is not covered on the Replay page. — [Replay](https://www.inngest.com/docs/platform/replay)
- Webhook transforms have a dashboard preview "with a sample payload before enabling production delivery," and cloud events can be sent to the local Dev Server. — [Webhooks](https://www.inngest.com/docs/platform/webhooks)

### Inferences
- For (b): Inngest's model is "runs are the replay unit". Remit already has a better substrate: a global-seq log plus a per-subscription cursor. Backfill is "create the subscription with `SeenSeq = N`" and dry run is "evaluate the condition over readings (N..head] and report would-fire rows without acting." This is a capability Inngest does not offer, and it is cheap for Remit because the log is local.
- The "Skipped" status shows that Inngest **records events that a paused function did not run on** and lets you replay them. That is the answer to (a) and (b) together: a pause or skip leaves a replayable record, never a hole.
- For (c): Inngest ties replay to *plan retention* and ignores consumer position. Remit can do better because subscriptions hold cursors. Retention should be `min(time policy, min(active subscription cursors))`, with a visible "subscription X is holding N readings" fact, or the replay/backfill window silently shrinks.
- Replay re-running side effects argues for keeping Remit's (subscription, key, revision) firing key: a replay should produce a *new revision* deliberately, never reuse the old key by accident.

### Limits that bound replay and waits
- Trace and log history by plan (Free / Pro / Business / Enterprise): "24 hours | 7 days | 14 days | Up to 365 days." Maximum function run length, including sleeps and `waitForEvent` time: 30 days / 90 days / 366 days / custom. `step.sleep` can last up to 1 year, within the plan's run length. Maximum event size: 256 KiB on Free, 3 MiB on paid plans. 5,000 events per send request. 1,000 steps per function. — [Inngest usage limits](https://www.inngest.com/docs-markdown/usage-limits/inngest)
- Inference: on the free tier, Replay reaches back at most 24 hours. Inngest's replay window is a billing knob, not a consumer guarantee, which reinforces the cursor-aware retention lesson for (c).

### Gaps
- The full list of replayable statuses (Cancelled? Failed only?) is not stated on the Replay page. Its only explicit statuses are failed-like runs, optional successful runs, and Skipped.
- No Inngest doc for "run function over historical events" was found. Treat it as absent, with MEDIUM confidence.

## 5. Observability: traces, "why didn't my function run", failure handling and dead-letter

### Takeaway
Inngest's event view shows each event's payload "and the functions it triggered." Runs have a step timeline with per-retry errors, and events and runs are searchable with CEL. Failures go to a per-function `onFailure` handler after retries are exhausted (0–20 retries, default 4), and to a global system event `inngest/function.failed` carrying `{error, event, function_id, run_id}`, which acts as a dead-letter stream that other functions subscribe to.

### Cited Findings
- Events view: filter by time or type, and "Open the event to inspect its payload and the functions it triggered." — [Inspecting function runs](https://www.inngest.com/docs/platform/monitor/inspecting-function-runs)
- Runs list filters by status, queued/started time and app. Run details show trigger, input, output, timing and a step timeline, and you can expand a failed step to see each retry's error. — [Inspecting function runs](https://www.inngest.com/docs/platform/monitor/inspecting-function-runs)
- CEL search over events and runs, with `event` and `output` variables, e.g. `output.success != true`. Errors are stored as JSON on `output`. — [Inspecting function runs](https://www.inngest.com/docs/platform/monitor/inspecting-function-runs)
- Retries: "Configure the number of times the function will be retried from 0 to 20. Default: 4." `onFailure` runs only after retries are exhausted. — [create reference](https://www.inngest.com/docs/reference/functions/create)
- `inngest/function.failed` "is sent whenever any single function fails in your Inngest environment." `data` holds `error` (message, name, stack), the original `event`, `function_id` and `run_id`. It "can be used to track all function failures in a single place," and SDK `onFailure` handlers are shorthand for this event scoped to one function. — [inngest/function.failed](https://www.inngest.com/docs/reference/system-events/inngest-function-failed)
- Webhook transform errors: a thrown error returns `400` (providers retry). A caught error that returns a diagnostic event returns `200`, which needs a catch-all function. — [Webhooks](https://www.inngest.com/docs/platform/webhooks)

### Inferences
- For (a): the key move is that **failure is itself an event on the same bus**. Remit should append a reading such as `remit/subscription.failed` (and `.skipped` with a reason) to its own log when a firing's action fails, when CEL evaluation errors, or when a reading is dropped by cooldown. Then the existing subscription machinery (tell the Assistant, open an inbox item) handles alerting, with no separate alert path. This also fits Remit's "facts Remit records about itself".
- "Event → functions it triggered" is the minimum for (g). For each reading, an agent tool should list every subscription considered and the outcome for each: `matched → firing F`, `condition false`, `condition error: …`, `pattern mismatch`, `cooldown`, `duplicate key`. Inngest documents only the positive edge (functions triggered). The negative edges are what makes "why didn't it fire" answerable. Hatchet's CEL `debug` (see §7) is the tool form of this.
- CEL search over runs/events is directly useful for agents (g): the same language they write conditions in is the query language for debugging.

### Gaps
- No Inngest doc was found that explains *why* a specific event did **not** trigger a function (e.g. "if expression false", "rate limited"). The fetched observability page does not cover skipped runs or reasons. LOW confidence that such a view exists.
- Other `inngest/*` system events were not enumerated on the page.

## 6. Webhook transforms as a door design

### Takeaway
Each Inngest webhook is a URL per provider with a small JavaScript transform `(evt, headers, queryParams, raw) → {name, data, id?, ts?}` that runs on Inngest's side. It maps the provider's payload to a namespaced event and can set `id` for dedupe. Inngest does **not** verify provider signatures; the docs require passing `raw` and the signature header through and verifying in the function. Allow and deny lists filter accepted event names and IPs.

### Cited Findings
- Transform inputs: `evt` (parsed JSON), `headers` (canonicalized), `queryParams` (arrays), `raw` (unmodified body). Output: `name` and `data`, plus optional `id` (dedupe) and `ts` (defaults to receipt time). Provider-prefixed names are recommended (`stripe/charge.failed`). — [Webhooks](https://www.inngest.com/docs/platform/webhooks)
- "Inngest does not check provider signatures." Without the check, "your function trusts any request sent to the webhook URL." A failed check should be a non-retriable error. — [Webhooks](https://www.inngest.com/docs/platform/webhooks)
- Allow and deny lists for event names and IP addresses. JSON is accepted, form encodings are in beta. Branch environments are chosen via `x-inngest-env`. Transforms can be managed through the REST API for version control. A preview with a sample payload is available. — [Webhooks](https://www.inngest.com/docs/platform/webhooks)

### Inferences
- The transform is a pure function at the boundary: payload in, normalized `{name, data, id, ts}` out. That matches Remit's "parse outside data once at the boundary" rule. Setting `id` from a provider delivery id (e.g. GitHub's `X-GitHub-Delivery`) gives door-level idempotency for free.
- Remit's door verifies signatures at the door (rails-and-sandbox), which is stronger than Inngest pushing verification into user code. Keep that.
- For (g), the transform preview is an agent tool: "run transform/condition against this sample payload and show the result", with no side effects. It is the same tool as the dry-run in §4.
- The 400-vs-200 trade-off is a real design question for Remit's door. A malformed payload that is acked and dropped is a silent skip (a). The Inngest answer (catch it and emit a diagnostic event) maps to appending a `door.rejected` reading.

### Gaps
- The transform runtime limits (CPU time, allowed APIs) were not stated on the fetched page.

## 7. Trigger.dev and Hatchet: where they differ meaningfully

### Takeaway
Trigger.dev is task-trigger-centric, not event-bus-centric. Its distinctive pieces are **idempotency keys with scopes and TTL** (30 days by default, auto-cleared on failure, resettable) and **waitpoint tokens** (a durable wait completed by an HTTP callback URL, an idempotency key on the token itself, and `{ok:false}` on timeout). Hatchet is closest to Inngest on events: wildcard event keys, CEL **filters as separate resources with a scope**, CEL concurrency keys with three explicit overflow strategies (round-robin queue, cancel-in-progress, cancel-newest), and a server-side CEL **debug** endpoint.

### Cited Findings
- Trigger.dev idempotency: a repeat trigger with the same key "returns the original run's handle." Scopes: `run` (default, hashed with the parent run id), `attempt` (parent run + attempt number), and `global`. Keys are always scoped per task and environment. — [Trigger.dev idempotency](https://trigger.dev/docs/idempotency)
- Trigger.dev `idempotencyKeyTTL`: "By default idempotency keys are stored for 30 days." "A failed run clears its key automatically"; successful and canceled runs keep theirs. `idempotencyKeys.reset(task, key)` and a dashboard reset exist. — [Trigger.dev idempotency](https://trigger.dev/docs/idempotency)
- Trigger.dev waitpoint tokens: `wait.createToken({timeout?, idempotencyKey?, idempotencyKeyTTL?, tags?})` returns `{id, url, publicAccessToken, isCached}`. `wait.forToken` returns `{ok, output}`, and "The only error that can occur is a timeout error." Completion is through `wait.completeToken`, an HTTP POST to `token.url` (server-to-server), or a CORS endpoint with `publicAccessToken`. Input streams use waitpoints internally. — [Wait for token](https://trigger.dev/docs/wait-for-token)
- Hatchet wildcard event keys: "As of engine version 0.65.0, Hatchet supports wildcard event triggers using the `*` wildcard pattern," e.g. `subscription:*`. — [Hatchet events](https://docs.hatchet.run/v1/events.md)
- Hatchet filters: created with a workflow id, CEL expression, `scope` and `payload`. A workflow with no filters triggers on every matching event. With filters, an event triggers only if its scope matches a filter and the expression is true. Declarative filters are replaced when the workflow updates (unstable IDs). — [Hatchet events](https://docs.hatchet.run/v1/events.md); [Hatchet event filters](https://docs.hatchet.run/v1/external-events/event-filters)
- Hatchet CEL: evaluated on the engine "before a task is ever assigned." A filter expression must return bool. "A failing filter expression means the filter does not match, so the run is not triggered." SDKs expose a CEL client `debug` method that evaluates an expression on the engine against a sample input, metadata and filter payload. — [Hatchet CEL expressions](https://docs.hatchet.run/v1/cel-expressions)
- Hatchet concurrency: the key is a CEL expression over input and metadata, with `max_runs` (itself computable per key). Strategies: **GROUP_ROUND_ROBIN** (queue per key, fair dequeue), **CANCEL_IN_PROGRESS** (newest wins), **CANCEL_NEWEST** ("the newly triggered run is cancelled immediately"). Multiple strategies can be stacked, and a key-expression evaluation failure fails the task. — [Hatchet concurrency](https://docs.hatchet.run/home/concurrency)

### Inferences
- Trigger.dev's "failed run clears its key" is a sharp idempotency rule. Remit already behaves this way, checked in code: a firing is inserted only after the processor returns, inside the same transaction as the subscription's progress (`internal/orch/plugin_pipeline.go:238-271`; `INSERT INTO firings ... ON CONFLICT DO NOTHING` at `internal/store/signal.go:204`). A failed action stores no firing, so the key stays free and the next pass retries. The gap is the other half of Trigger.dev's model. A failure that is not an admission hold or a busy routine reaches only `o.log.Error("fire", ...)` and `return started, true` (`internal/orch/signals.go:318-320`). It is retried every pass with no attempt count, no backoff, no terminal "failed" state and nothing shown to the owner. That is problem (a) located: Inngest's retries 0–20 + `onFailure` + `function.failed`, and Trigger.dev's explicit failed status, are the missing pieces. HIGH (code read).
- The TTL on idempotency keys is the retention question (c) in miniature: the firing record must outlive the reading's retention, or a re-delivered reading fires again.
- Waitpoint tokens with a callback URL are the "door per wait" pattern: the external system completes exactly one wait, with no subscription matching needed. That is a cleaner fit than a subscription for one-shot callbacks (approval links, a CI job finishing).
- Hatchet's overflow trio maps one-to-one onto "one run at a time" choices Remit leaves implicit (e): queue (round-robin), replace (cancel-in-progress), and drop-new (cancel-newest = Inngest singleton `skip`). Inngest singleton covers only `skip` and `cancel`; Hatchet adds `queue`.
- Hatchet's **condition evaluation error → no match, no run** is exactly the silent-skip failure mode (a). Remit should avoid it: a CEL runtime error on a reading must be recorded and surfaced, not treated as `false`. Hatchet's `debug` endpoint is the mitigation and a direct model for an agent tool (g): `subscription.test(condition, reading_seq | sample)`.
- Hatchet's filter `scope` + `payload` separates *what the subscriber wants* (expression and its parameters) from *the trigger declaration*. That corresponds to Remit subscriptions created by agents at runtime, as opposed to triggers declared in code. Unstable IDs for declarative filters is a warning: agent-created subscriptions need stable identity across playbook updates.

### Trigger.dev concurrency and run TTL
- Runs wait in a queue and only executing runs hold slots: "Runs that are delayed or waiting in a queue do not consume concurrency slots until they begin execution." `concurrency: {total: n}` caps all runs of a task. `concurrency: {perKey: n}` caps each `concurrencyKey` pool separately. Named `concurrencyLimit()` pools can be shared across tasks, and a run starts only when every limit it holds has capacity. Over-limit runs stay queued and nothing is dropped. A run that checkpoints at a waitpoint releases its slots and must reacquire them on resume; waits under 60 s keep the slot. — [Trigger.dev queue concurrency](https://trigger.dev/docs/queue-concurrency)
- Run TTL: "the maximum duration a run can remain in a queued state before being automatically expired," which ends with status `Expired`. It can be set per trigger, per task or in global config. Dev runs default to 10 minutes. Cloud staging and production default to and cap at 14 days. — [Trigger.dev runs: TTL](https://trigger.dev/docs/runs#time-to-live-ttl)
- Neither the concurrency page nor the runs page mentions a trigger-level debounce. — [queue concurrency](https://trigger.dev/docs/queue-concurrency); [runs](https://trigger.dev/docs/runs#time-to-live-ttl)
- Inference: TTL plus an explicit `Expired` status is the model for Remit's deadline window. A firing that could not act before its deadline should end as a visible terminal outcome (`expired`), never a disappearance (a, e). Trigger.dev's "slots released while waiting" matches Inngest concurrency counting only executing work. For Remit, "one at a time" must state whether a chain parked in a wait counts as busy.

### Hatchet durable event waits (lookback)
- Durable tasks wait on events (`ctx.aio_wait_for_event` in Python, `ctx.waitForEvent` in TS, `ctx.WaitForEvent` in Go, `ctx.wait_for` with `UserEventCondition` in Ruby), optionally with a CEL filter on the payload such as `input.user_id == '1234'`. The event key must match exactly. — [Hatchet durable event waits](https://docs.hatchet.run/llms/v1/durable-event-waits.md)
- **Lookback**: a wait can match events "pushed up to a minute before this wait was registered" (the examples set `1m`; no default is stated). Lookback requires a **scope** pushed with the event, which is "a hint to help Hatchet narrow down the pool of candidate events." Ruby lacks lookback ("coming soon"). — [Hatchet durable event waits](https://docs.hatchet.run/llms/v1/durable-event-waits.md)
- "Even if the task is interrupted and requeued while waiting, the event will still be processed": on resume the task reads the event from the durable event log. — [Hatchet durable event waits](https://docs.hatchet.run/llms/v1/durable-event-waits.md)
- At `SleepFor`/`WaitForEvent`/`WaitFor`, Hatchet checkpoints, frees the worker slot, and re-queues the task when the event arrives or the sleep ends. — [Hatchet task eviction](https://docs.hatchet.run/llms/v1/task-eviction.md)
- Hatchet has no timeout parameter on an event wait. A timeout is an **or group** of a sleep and an event: `or_(SleepCondition(duration=timedelta(minutes=1)), UserEventCondition(event_key="wait_for_event:start"))`. The group "evaluates to `True` as soon as at least one of the conditions inside it is satisfied," and several or groups on one task "are combined with `AND`." DAG tasks also take `skip_if` / `cancel_if`, which are CEL over the parent's `output`, and a cancelled task cancels its dependents. — [Hatchet DAGs: or groups](https://docs.hatchet.run/v1/directed-acyclic-graphs); [Hatchet durable execution](https://docs.hatchet.run/home/durable-execution)
- Hatchet replay is checkpoint replay, not event replay. At each wait or child spawn "Hatchet writes a checkpoint to the durable event log," and "On retries, Hatchet can replay from that checkpoint instead of re-running completed application logic." "The code between checkpoints must be deterministic." — [Hatchet durable tasks](https://docs.hatchet.run/llms/v1/durable-tasks.md)
- Inference for (d): Hatchet's lookback is the explicit admission that forward-only waits race with event arrival, which Inngest leaves unstated. Remit's global seq gives the exact form of this: a wait records `from_seq` (or a chosen earlier seq) instead of a time-based lookback plus a scope hint.
- Inference for (e): Hatchet expresses "deadline OR event" as a boolean composition of a time condition and an event condition in one wait. That is one way to put clock and subscription windows under one model: a deadline is just a time condition in the same group, not a separate mechanism.

### Trigger.dev bulk replay
- `runs.bulk.replay()` takes either a `filter` (run-list fields such as `status`, `taskIdentifier`, `period`, `from`/`to`) or `runIds`, not both. "The action defaults to the **last 7 days** and won't target older matching runs" when no time bound is given. "Each environment can only run a limited number of bulk replays at the same time" (the number is not stated). `runs.bulk.abort()` is "best effort." "When omitted, each replay keeps the original run's region." — [Trigger.dev bulk actions](https://trigger.dev/docs/runs/bulk-actions)
- A single replay is "a copy of a run with the same payload but against the latest version in that environment." "A replay starts a new run" with a new id. The SDK can override `payload` or pin a `version`, and the UI lets you edit the payload before replaying. — [Trigger.dev replaying](https://trigger.dev/docs/replaying)
- Hatchet Python `ctx.aio_wait_for(signal_key, *conditions, label=None)` takes `SleepCondition | UserEventCondition | OrGroup` and returns `dict[str, Any]`, "A dictionary containing the results of the wait." — [Hatchet Python context reference](https://docs.hatchet.run/reference/python/context)
- Inference for (b): Trigger.dev, like Inngest, replays *runs*, selected by filter and bounded in time. None of the three platforms documents running a new consumer over historical events. Backfill from a cursor is Remit-native ground with no prior art in this set. Trigger.dev's "replay with an edited payload" is a dry-run/debug affordance worth copying for agents (g): re-judge a subscription against an edited reading.

### Gaps
- The keys of Hatchet's `aio_wait_for` result dictionary, and so how a caller tells which condition in an or group fired, are not documented in the Python reference or the DAG, durable-tasks and durable-event-waits pages. Only the Hatchet SDK source would answer it, and reading that is outside this docs-scoped research.
- Neither the Trigger.dev replaying page nor the bulk-actions page lists which run statuses can be replayed.
- The full list of statuses Inngest Replay accepts is not on [the Replay page](https://www.inngest.com/docs/platform/replay), which names only failed runs, optional successful runs and Skipped. Confirming the rest needs the dashboard (an Inngest account), which this research did not use.

## 8. Mechanism → Remit open problem map (summary of inferences above)

### Takeaway
The highest-value lessons: make every non-firing a recorded outcome with a reason, emitted as a reading on the same log (a). Use the global seq for start positions, backfill and dry run, which Inngest cannot do (b). Make retention cursor-aware (c). Name the overlap policy as an explicit enum: drop / delay / collapse / queue / replace (e). Give processors an enforced finish timeout outside the lock (f). Give agents a server-side "test this condition against this reading" tool and a per-reading "subscriptions considered and outcome" view (g).

### Cited Findings
- (a) silent fail/skip: `inngest/function.failed` as a global failure event ([source](https://www.inngest.com/docs/reference/system-events/inngest-function-failed)). Duplicate events "still stored, but no new run" ([source](https://www.inngest.com/docs/events)). "Skipped" status for paused functions is replayable ([source](https://www.inngest.com/docs/platform/replay)). Counter-example: Hatchet treats a filter eval error as no match ([source](https://docs.hatchet.run/v1/cel-expressions)).
- (b) start position, backfill, dry run: Replay by time range/status, bounded by retention ([source](https://www.inngest.com/docs/platform/replay)). Transform preview ([source](https://www.inngest.com/docs/platform/webhooks)). Hatchet CEL `debug` ([source](https://docs.hatchet.run/v1/cel-expressions)).
- (c) retention vs cursors: replay availability "depends on your plan's event retention" ([source](https://www.inngest.com/docs/platform/replay)). Trigger.dev idempotency TTL is 30 days by default ([source](https://trigger.dev/docs/idempotency)).
- (d) state vs stream: waitForEvent is forward-matching on a later event (`async`) against the trigger (`event`) ([source](https://www.inngest.com/docs/reference/functions/step-wait-for-event)). Payload version `v` ([source](https://www.inngest.com/docs/features/events-triggers/event-format)).
- (e) time and overlap: cron as a trigger with overlapping schedules deduplicated ([source](https://www.inngest.com/docs/reference/functions/create)). Rate limit / throttle / debounce / singleton / priority semantics and processing order ([source](https://www.inngest.com/docs/guides/flow-control), [source](https://www.inngest.com/docs/guides/singleton)). Hatchet's three strategies ([source](https://docs.hatchet.run/home/concurrency)).
- (f) processor under lock with no timeout: `timeouts.start`/`finish` on runs ([source](https://www.inngest.com/docs/reference/functions/create)). Hatchet evaluates CEL on the engine before assignment, so user code never runs in the matcher ([source](https://docs.hatchet.run/v1/cel-expressions)).
- (g) agents create and debug subscriptions: CEL everywhere (triggers, keys, waits, search) ([source](https://www.inngest.com/docs/reference/functions/create), [source](https://www.inngest.com/docs/platform/monitor/inspecting-function-runs)). Event view lists the functions triggered ([source](https://www.inngest.com/docs/platform/monitor/inspecting-function-runs)). Hatchet `debug` ([source](https://docs.hatchet.run/v1/cel-expressions)).

### Inferences
- (f) is not directly answered by any of the three platforms, because none of them run user code inside their matcher. All three split it in two: a pure, fast, non-Turing-complete matcher (CEL) runs in the engine, and user code runs as a separate run with timeouts and retries. The structural lesson for Remit: a plugin processor is an *action* (a run), not part of matching. Matching under the global mutex should be CEL-only. The processor should run outside the lock with a finish timeout, and its result should come back as a new reading (append under the lock). Fit checked in code: `Tick` takes `o.tickMu.Lock()` (`internal/orch/schedule.go:67`) and calls `o.tickSignals` under it (`schedule.go:78`). That reaches `judge → settle → fire → process` (`internal/orch/signals.go:197, 306, 356`), and `pluginProcessing.Process` calls `p.o.runner.Process(ctx, ref, req)` synchronously (`internal/orch/plugin_pipeline.go:244`) with the tick's `ctx`. `rg WithTimeout` finds no timeout in `internal/plugin/` outside a test or in `plugin_pipeline.go`. A slow plugin therefore stalls the whole tick, including chain starts (`runReady`, `schedule.go:81`). The existing transaction shape already separates "act" from "record firing + progress". Moving the act out of the tick and bounding it is a structural change, not a rewrite. HIGH (code read) on the current behavior, MEDIUM on the size of the change.
- (e): all three platforms treat cron as a trigger, and none treats it as an emitted event. Remit's choice (clock as a source of readings) is defensible and more inspectable. The windows (cooldown, deadline) then become flow-control properties of the subscription, named after Inngest's vocabulary.
- One consistent pattern across all three: **one expression language (CEL) for conditions, keys, priorities and search**. Remit already uses CEL for conditions. Extending it to the dedupe key, the one-at-a-time key and the overlap key would give agents a single language to learn and debug (g).

### Gaps
- None of the sources shows how these platforms handle a slow subscriber holding back retention. They are hosted queues with time-based retention, not cursor-based logs. Problem (c) has no direct prior art in this set; Kafka/NATS JetStream consumer-aware retention would be the closer comparison and was out of scope.
